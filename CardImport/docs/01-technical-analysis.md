# 名片 → iPhone 聯絡人：技術分析與架構決策

本文件回答規格第 36 節的 1–12 項。第 13 項（實作）在 `Packages/CardCore` 與 `App/`。
所有決策依規格的優先順序：**準確度 > 人工介入最少 > 步驟最少 > 速度 > 成本**。

---

## 1. iOS 原生限制與可行性

| 需求 | iOS 能做到的事 | 限制 | 本專案做法 |
|---|---|---|---|
| NFC 一碰啟動 | 「捷徑」個人自動化的 NFC 觸發器可設定「立即執行」，不需確認 | 第三方 App 不能自己註冊 NFC 自動化，需使用者在「捷徑」設定一次（約 30 秒） | App 提供 App Intent「匯入名片」（AppShortcutsProvider，免自建捷徑）。NFC 自動化 → 匯入名片 → App 開啟並**直接顯示照片多選畫面** |
| 不用 App 也能 NFC | NFC 貼紙寫入 URL（`cardimport://import`），iPhone 背景讀取標籤 | 背景讀取會先跳出通知橫幅，要多點一下 | 支援，作為備案 |
| 大量選照片 | PhotosPicker 無數量上限，選取不需要相簿權限 | 系統的「加入」鈕無法省略 | 這一下就是規格中的「按一次開始」，選完自動開始處理 |
| 從「照片」分享 | Share Extension | 記憶體上限約 120 MB；官方 API 不能從延伸打開主 App | 延伸內直接跑同一套流程並顯示進度與完成畫面；若中途關掉，狀態已存檔，主 App 下次開啟自動接續 |
| 拍攝時間（配對正反面） | 從影像資料讀 EXIF `DateTimeOriginal` | 不需相簿權限 | 用於正反面配對（相鄰拍攝） |
| 寫入聯絡人 | Contacts framework（CNContactStore） | iOS 18 起使用者可選「有限取用」，重複檢查只看得到被分享的聯絡人 | 要求完整取用；有限取用時在設定頁提示 |
| 寫入「備註」欄位 | `CNContact.note` | **需要 Apple 核准的特殊權限** `com.apple.developer.contacts.notes`（需付費開發者帳號申請） | 語音備註預設存在 App 內；取得權限後在設定開啟即寫入通訊錄備註 |
| 背景處理 | `beginBackgroundTask` 約 30 秒 | 長批次離開 App 後可能被暫停 | 每一步都存檔；回到 App 或下次開啟自動接續，不會重複建立 |
| 安裝到自己的手機 | 需要 Mac + Xcode | 免費 Apple ID 安裝 7 天後要重簽；付費開發者帳號（US$99/年）可用 TestFlight 長期使用 | 專案用 XcodeGen 產生，見 `App/README.md` |

結論：**原生 iOS App + Share Extension + App Intent** 是唯一能同時做到「NFC 一碰」、「從照片分享」、「讀通訊錄去重」、「直接寫入聯絡人」的方案。網頁或 PWA 無法讀取通訊錄，因此無法去重，只能產生 .vcf 讓使用者手動匯入，所以不採用。

## 2. 實際操作步驟（最少動作）

**方法 A（NFC）**：碰 NFC 貼紙 → 照片多選畫面直接出現 → 勾選照片 → 按「加入」→ 自動處理 → 完成畫面。
使用者動作：**1 碰 + 勾照片 + 1 按**。

**方法 B（照片 App）**：照片 → 選取 → 分享 → 名片匯入 → 自動處理 → 完成。
使用者動作：**選取 + 分享 + 1 按**。

**完成畫面**只有數字、「確認 N 項」（有待確認時才出現）和「完成」。高信心的聯絡人不會問「是否建立」或「是否儲存」。

**一次性設定**（第一次開 App）：貼上 API 金鑰、允許聯絡人、設定 NFC 自動化（選用）。

## 3. 辨識方案比較

| 方案 | 準確度（名片情境） | 人工介入 | iOS 整合 | 隱私 | 速度 | 成本 | 開發複雜度 |
|---|---|---|---|---|---|---|---|
| A. Apple Vision OCR + 規則 | 字元辨識好；**欄位分類弱**（姓名、公司、職稱、標語容易混淆，中英混排更差） | 高 | 最好 | 全在手機 | 快（<1 秒/張） | 免費 | 低 |
| A2. Vision + Apple Foundation Models（裝置端 LLM） | 比 A 好；裝置端小模型對中英混排、繁簡、正反面推理較弱；需 Apple Intelligence 機型 | 中 | 好 | 全在手機 | 中 | 免費 | 中 |
| B. 第三方 OCR / 名片 API（Google Vision、Azure、ABBYY、CamCard 等） | 字元準；欄位分類各家差異大；Azure 名片模型已停用 | 中 | 需自己串 | 上傳第三方 | 中 | 付費 | 中 |
| C. 多模態視覺 AI 直接讀圖（Claude） | **最高**：同時「看」排版與語意，能分辨標語、Logo 字、雙語姓名 | 低 | 需自己串 | 上傳 Anthropic | 數秒/張，可平行 | 每張約 US$0.03–0.05（估計） | 中 |
| **D. 混合：Vision OCR + Claude + 驗證器 + 第二模型複核（採用）** | **最高，且有獨立交叉驗證** | **最低** | 好 | 圖片上傳 Anthropic；OCR 在手機 | 數秒/張，可平行 | C 的成本 + 少量複核 | 高 |
| E. 完全自建模型 | 需要大量標註資料，短期內不可能超過 C | — | — | — | — | 極高 | 極高 |

**為什麼選 D 而不是 C**：單一模型自己報的信心值不夠可靠。D 加入兩個**獨立**的證據來源：
1. **手機端 OCR 轉寫**：與 AI 讀到的值比對，例如電話差一碼就判定為衝突。
2. **另一個模型的第二意見**：只針對不確定的欄位詢問。

再加上格式驗證，信心分數才有意義。只有這三者都無法確定時才問使用者。這直接對應規格第 13 節的「AI 能自己解決的，不要丟給使用者」。

**為什麼不選 A 當主力**：規則能分出 email、電話、網址，但姓名、公司、職稱、標語的分類靠位置和字型，遇到中英混排或設計感名片會大量出錯，需要人工確認，違反最高 KPI。A 仍保留為「離線/免費模式」與 benchmark 對照組（`HeuristicExtractor`）。

## 4. Benchmark 方法

`benchmark/` 內含：
- **資料集產生器**：用 HTML/CSS 版型渲染名片，再模擬手機拍攝（傾斜、陰影、光線不均、模糊、JPEG、桌面背景）。涵蓋規格第 21 節的各種情況，每張照片都有標準答案。
- **跑分程式**：直接呼叫與 App **同一套** Swift 核心（`cardcore-cli`），只把 Apple Vision 換成 tesseract、把通訊錄換成記憶體版本。
- **評分程式**：計算規格第 22 節的所有指標。

| 指標 | 定義 |
|---|---|
| Field Accuracy | 每個欄位（姓名/公司/職稱/電話/Email/地址…）最終寫入值與標準答案一致的比例 |
| Contact Accuracy | 整個聯絡人所有欄位都正確、沒有多餘錯誤值的比例 |
| Human Intervention Rate | 需要使用者處理至少一項的人數 ÷ 總人數 |
| Wrong Auto-Save Rate | 未經確認就寫入、但含錯誤值的聯絡人比例（最重要的安全指標） |
| Pairing | 正反面配對的精確率與召回率；錯配一律視為嚴重錯誤 |
| Duplicate Detection | 預先放入通訊錄的既有聯絡人與誘餌，看是否正確「更新、略過或新建」 |
| Time / Cost | 每張平均秒數、API token 與美元成本 |

**真實名片驗收**：模擬資料只能比較方案和調整門檻。最終驗收必須用你的真實名片照片，流程見 `benchmark/README.md`。

## 5. 架構決策

```
照片 ─► 前處理（裁切卡片、轉正、縮圖、EXIF 時間、顏色特徵）
      ─► Apple Vision OCR（裝置端，獨立第二讀者）
      ─► Claude 視覺擷取（結構化 JSON、每欄位信心值、忽略標語清單）
      ─► 單張驗證（電話號碼規則、Email 修復、網域一致、郵遞區號、姓名形狀、OCR 交叉比對）
      ─► 正反面配對（可解釋的評分 + 必要時文字模型仲裁）
      ─► 合併（兩面一致 → 信心上升；衝突 → 下降並保留候選）
      ─► 第二模型複核（只針對不確定欄位）
      ─► 欄位層級政策（自動寫入 / 保留待確認 / 視為雜訊）
      ─► 通訊錄去重（新建 / 補充既有 / 已存在 / 可能重複）
      ─► 寫入 Contacts ─► 完成摘要 + 待確認清單
```

模型預設：
- **擷取**：`claude-opus-5-5`，effort medium。
- **複核**：`claude-opus-5-5`，effort high。只針對單一欄位提出窄問題。這是 benchmark 實際量過的組合。
- **配對仲裁與語音整理**：`claude-opus-5-5`。

設定中可把複核改為 `claude-fable-5-1`：模型能力更強、和擷取模型的錯誤更獨立，但較貴。

## 6. 可以完全免費的部分

- 裝置端：拍攝時間讀取、卡片裁切、透視校正、Apple Vision OCR、顏色特徵。
- 所有驗證器：電話（E.164）、Email 修復、網址、地址/郵遞區號、中文姓氏與拼音/威妥瑪/粵拼對照。
- 正反面配對評分、合併、去重、批次狀態保存與續跑。
- 寫入通訊錄、語音轉文字（Apple Speech）。
- 「離線模式」：Vision OCR + 規則，完全免費。benchmark 顯示規則式欄位分類在一般門檻下會讓約一半聯絡人被寫入錯誤值，所以此模式改用最嚴格門檻（0.98／0.97）：不寫錯，但幾乎每位都要確認。只是斷網時不需要切換到此模式，AI 模式會暫停並在連線後自動續跑。

## 7. 使用 AI API 明顯提升準確度的部分

| 環節 | 為什麼需要 AI | 成本（估計） |
|---|---|---|
| 欄位語意分類（姓名/公司/職稱/標語） | 規則無法可靠分辨，這是人工介入的主要來源 | 擷取請求的主要成本 |
| 中英雙語姓名對應、繁簡、直式排版 | 需要理解語意 | 同上 |
| 不確定欄位的第二意見 | 讓多數低信心欄位不必問人（benchmark：人工介入從 76% 降到 7%） | 平均每張照片約 0.9 次，每次約 US$0.02–0.05（Opus 5.5） |
| 無姓名背面的歸屬仲裁 | 只送文字摘要，便宜 | < US$0.01 |
| 語音備註整理 | 選用 | < US$0.01 |

## 8. Contact JSON Schema

- 模型輸出格式：`schema/extraction-api.schema.json`（由 `cardcore-cli schema` 產生，與程式碼同步）。
- 欄位說明版：`schema/contact-candidate.schema.json`。
- 每個值都附 `confidence`、`alternatives`、`source_text`。沒有印在名片上的一律為 `null`，禁止猜測。
- `evidence.ignored_text` 記錄刻意不寫入的標語、Logo 字、認證標章。

## 9. Confidence / Review 邏輯

最終信心用 log-odds 累加，起點是模型自報的信心值：

| 訊號 | 調整 |
|---|---|
| OCR 逐字吻合 | +1.2 |
| OCR 僅差易混字（0/O、1/l、5/S） | +0.2 |
| OCR 讀到相近但不同的值（例如電話差一碼） | **−2.5**，乘以 OCR 可靠度權重 |
| OCR 完全沒有 | −1.6，乘以 OCR 可靠度的平方 |
| 格式不合法（電話號碼規則、Email 語法） | −2.6 |
| Email 網域與網站一致 | +0.8 |
| 兩面都讀到同一值 | +1.5 |
| 兩面讀到不同值 | −2.0 |
| 第二模型同意 | +2.0 |
| 第二模型不同意 | −2.5 |
| 中英文姓名姓氏對得上 | +1.0 |
| 「公司」看起來像標語 | −1.5 |

**OCR 可靠度**：每張照片先算「模型有把握的值中，OCR 也讀到的比例」。
- 模糊、字型特殊、中文難讀的照片，OCR 可靠度低，OCR 沒讀到不代表 AI 錯。
- OCR 讀得好的照片若漏讀某個值，則是有意義的反證。
- 這是 benchmark 中最大的改善來源：原本被送去確認的欄位有 93% 其實是對的。

政策（`PolicyConfig`，以 benchmark 校準）：
- 姓名、電話、Email 需 ≥ 0.90；其他欄位需 ≥ 0.85，否則**只有該欄位**保留待確認，其他欄位照常寫入。
- 低於 0.30 且沒有候選值，視為雜訊，不寫也不問，只記錄在處理紀錄。
- 只有**姓名全部不確定**時才暫緩建立整個聯絡人，而且只問姓名一題。
- **模型自己列出替代讀法的欄位**（例如「恆／恒」），即使信心值過門檻，也一定要經過獨立確認才寫入：第二意見、另一面一致或使用者確認。只差大小寫或標點的替代讀法不算。
- 第二意見的比對是**逐字精確**的，異體字（恆／恒、滙／匯）視為不同值。
- 先由第二模型複核，仍不確定才進入待確認清單。
- 待確認清單提供候選值按鈕、「自行輸入」和「留空」，並附原始照片。

## 10. 正反面配對邏輯

兩張照片的配對分數由以下證據組成：

| 層級 | 證據 | 分數 |
|---|---|---|
| 個人層級 | 同 Email | +4 |
| 個人層級 | 同手機 | +3.5 |
| 個人層級 | 同姓名 | +3 |
| 個人層級 | 中英姓名對應 | +2.5 |
| 公司層級（合計上限 2.5） | 同公司、同網域、同總機、同地址 | 各自加分，合計不超過 2.5 |
| 輔助 | 一面有姓名一面沒有 | +0.8 |
| 輔助 | 正面/背面標記相反 | +0.5 |
| 輔助 | 拍攝時間 ≤20 秒 | +2.5 |
| 輔助 | 拍攝時間 ≤60 秒 | +1.5 |
| 輔助 | 拍攝時間 >10 分鐘 | −1 |
| 輔助 | 顏色相似 | +0.8 |
| 輔助 | 選取順序相鄰 | +0.3 |
| 否決 | **兩面姓名不同** | 永不合併 |
| 矛盾 | 兩面都有 Email 但網域完全不同 | −4 |
| 矛盾 | 兩面都有手機但號碼不同 | −3 |

公司層級證據設上限，是因為同事的名片背面通常一模一樣：它只能說明「同公司」，不能說明「同一人」。

benchmark 後補上的規則：
- **必須有內容證據**：任何合併都要求內容分數 ≥ 1.5，也就是至少有一項身分證據或公司層級證據。拍攝時間、顏色、正反面標記只能在候選之間分高下，不能單獨造成合併。
- **姓名比對嚴格化**：
  - 英文姓名必須完全相同，或只差 OCR 易混字。Chang 和 Zhang 是不同人。
  - 中文姓名在繁簡轉換後必須相同。
  - 只有姓氏對得上的中英對應（例如 Wang ↔ 王）是弱證據，只加 0.5 分；名字的拼音也對得上才加 2.5 分。
- **拍攝時間最近鄰**：無姓名背面在 30 秒內最接近的照片，若屬於某位有內容關聯的候選人，該候選人加 1.5 分。

- 有姓名的照片先依分數 ≥ 3 合併，並檢查群組內沒有姓名衝突。
- 沒有姓名的背面：只有在第一名比第二名高出 1.5 分以上時才自動歸屬；否則先交給文字模型仲裁（只送摘要，接受門檻是信心 ≥ 0.85）；仍不確定才問使用者「這張背面屬於哪一位？」。
- 沒有任何聯絡資訊的裝飾性背面直接忽略，不問。

## 11. Duplicate Detection 邏輯

查詢通訊錄的方式：依 Email、依電話（`predicateForContacts(matching:)`）、依英文與中文姓名。

| 證據 | 分數 |
|---|---|
| 同 Email | +0.6 |
| 同手機 | +0.5 |
| 同辦公電話 | +0.25（可能是同事共用） |
| 同姓名 | +0.35 |
| 中英姓名對應 | +0.2 |
| 同公司 | +0.15 |
| 姓名明顯不同 | −0.6 |

| 分數 | 判定 | 動作 |
|---|---|---|
| ≥ 0.75 且沒有新資料 | 已存在 | 略過 |
| ≥ 0.75 且只有新增資料 | 同一人 | 自動補上新電話、新 Email 等，不覆蓋舊值 |
| ≥ 0.75 且公司或職稱不同 | 可能換工作 | 新增資料照補；只把「要不要更新公司/職稱」放進待確認 |
| 0.45–0.75 | 可能重複 | 待確認：「和通訊錄裡的 X 是同一人嗎？」 |
| < 0.45 | 新聯絡人 | 新建 |

只有姓名相同不足以判定重複（同名同姓很常見）。

## 12. 批次處理架構

- `BatchState` 每一步都以原子寫入存成 JSON（App Group 容器）。App 被殺、當機、斷網後重新開啟，會從中斷處接續。
- **辨識**：每張照片獨立平行處理（預設 4 個並行）。
  - 暫時性錯誤（逾時、429、5xx）自動退避重試。
  - 單張永久失敗不影響其他照片，在完成畫面列為「無法辨識」並可一鍵重試。
  - 全部都連不上視為離線，暫停並在恢復網路後自動接續。
  - API 金鑰錯誤只提示一次，不會逐張報錯。
- **寫入**：依序寫入，讓後面的人能看到前面剛建立的聯絡人。
  - 寫入前一定先去重，所以「寫入後、存檔前」當機重跑時，會找到剛建立的聯絡人並判定已存在，不會重複建立（有單元測試驗證）。
- **暫存圖片**：處理完自動刪除；有待確認項目的照片保留到確認完成。從「照片」選的原始照片永遠不動。
- **處理紀錄**：每批的照片數、人數、建立/更新/已存在/待確認/失敗、成本、時間、配對證據都保存在批次 JSON 中，30 天後清除。這些資訊不會增加任何操作步驟。
