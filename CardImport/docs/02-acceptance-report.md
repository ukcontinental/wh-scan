## 測試資料

模擬資料集由程式產生：
1. 名片用 HTML 版型渲染。
2. 再模擬手機拍攝：傾斜 2–8°、陰影、光線不均、模糊、反光、JPEG 壓縮、木桌／白桌／布料背景、900–2400 px 解析度。

涵蓋規格第 21 節的各種情況：

| 類別 | 內容 |
|---|---|
| 文字 | 英文、繁中、簡中、中英混排 |
| 版面 | 直式、橫式、直書中文 |
| 雙面卡 | 另一語言版本；只有聯絡資訊、沒有姓名；只有 Logo＋網址＋QR；純裝飾 |
| 干擾元素 | 大 Logo、QR Code、人物頭像、標語、認證標章 |
| 多組資料 | 多支電話（手機／辦公／傳真／分機）、多個 Email、雙地址 |
| 字體 | 小字、特殊字型 |
| 易混淆 | 姓名與公司名容易混淆（例如 Chan & Chan Trading 的 Victoria Chan） |

去重測試：先在通訊錄放入 4 位資料不完整或公司已過時的既有聯絡人，以及 2 位同名不同人的誘餌。

兩種情境：
- **有拍攝時間**：照片保有 EXIF，模擬「每張先拍正面再拍背面」。
- **無拍攝時間**：截圖或轉傳圖片，沒有 EXIF。

選取順序一律打亂，正反面不相鄰。

怎麼讀這張表：
- **免費方案不可用**：近一半到六成的聯絡人被自動寫入錯誤資料，沒有一位能免人工完全正確。這印證了技術分析中「不採用規則式 OCR 當主力」的決策。
- **第二意見是關鍵**：沒有複核時，七成以上的人要確認；加入只針對不確定欄位的第二意見後，降到一成以下。
- **拍攝時間很重要**：同公司同事的名片背面常常一模一樣，沒有 EXIF 時，系統只能問「這張背面屬於誰」（保留集 3 題）。正常用手機連拍正反面就不會有這個問題。即使沒有拍攝時間，**錯配仍是 0**：無法確定時一律問人，不會亂合併。

## 保留集：誠實的首次結果與修正

開發集的規則是看著開發集調的，數字一定偏樂觀。所以另外產生從未看過的保留集：

**首次跑（未修改任何程式）**：有拍攝時間時，錯誤自動存檔率 10%（3 人），高於開發集。原因是 4 個真正的程式錯誤，不是門檻問題：

1. **香港電話被改成 +1**：第二意見回來後，程式用裝置預設地區（加拿大）重新正規化號碼。改為用該號碼自己的國碼。
2. **北京市話 (010) 被判無效**：國碼後 10 開頭被誤當成手機格式。
3. **地址被靜默丟棄**：第二意見只是少寫郵遞區號就被判「不同意」，信心降到門檻以下後被丟掉。改為曾經被複核過的值絕不靜默丟棄，而且比對時容許郵遞區號有無。
4. **網址比對過嚴**：`www.x.com` 和 `https://www.x.com` 改為比較網域。

另外，號碼規則驗證不過的電話，現在不論兩個模型怎麼說，都不會自動寫入。

修正後，開發集數字完全不變，保留集錯誤自動存檔降到 3.3%。**修正後的保留集數字已不再是完全不偏的估計**，首次跑的數字才是。實際表現可能介於兩者之間。

**剩下那 1 個錯誤**：台灣銀行名片上的英文 Logo 字「HEBANG BANK」被寫進「公司（英文）」。中文公司名「合邦商業銀行」正確。標準答案把這行算作 Logo 字（不應寫入），但它其實也是該銀行的英文名稱。這屬於判斷邊界，我沒有為了分數修改規則。

## 開發集的改善過程

| 版本 | 免人工完全正確 | 人工介入 | 錯誤自動存檔 | 主要改動 |
|---|---|---|---|---|
| 初版 | 13.3% | 86.7% | 4.4% | — |
| v1 | 24.4% | 75.6% | 0% | OCR 可靠度加權、無「+」國碼解析、合併必須有內容證據、只有姓氏的中英對應降權 |
| v2 | 75.6% | 20.0% | 4.4% | 加入第二意見複核（發現「恆／恒」被繁簡轉換誤判為同意） |
| v3 | 80.0% | 20.0% | 0% | 逐字精確比對、模型自己列出替代讀法的欄位必須確認、複核請求附上欄位情境、姓名比對嚴格化（Chang≠Zhang） |
| 最終 | 93.3% | 6.7% | 0% | 拍攝時間最近鄰、雙語替代讀法歸位、複核上限提高到每人 8 個 |

最有價值的發現：被送去人工確認的欄位裡，**93% 其實是對的**。原因是當 OCR 本身讀得很差時，系統卻把「OCR 沒讀到」當成反證。改成依每張照片的 OCR 可靠度加權後，大幅減少不必要的確認。

## 獨立程式碼審查

另一個子代理對整個專案做了獨立審查，找到 14 個真實問題，已全部修正並補上回歸測試。修正後 benchmark 數字不變。最重要的幾個：

| 問題 | 後果 | 修正 |
|---|---|---|
| 分享延伸暫存的批次，在 App 沒有聯絡人權限時恢復 | 整批人被標成失敗，照片被刪，永久遺失 | 沒權限時暫停（人保持待寫入、照片保留），恢復前先要求權限 |
| 待確認畫面連點兩下 | 建立兩個聯絡人 | 答案只處理一次、依序執行、按下後按鈕停用 |
| 寫入後、存檔前當機，且卡片沒有手機或 Email | 續跑時建立重複聯絡人 | 寫入前先標記「寫入中」；通訊錄已有卡片上全部資料時視為同一人 |
| 背面歸屬到尚未寫入的人 | 被暫緩的不確定欄位被直接寫入 | 合併後重新套用欄位審核規則，保留使用者先前的答案 |
| 審核時改正非北美電話 | 被加上 +1 國碼 | 用原號碼的國碼正規化 |
| App 與分享延伸同時處理同一批次 | 重複呼叫 API、互相覆蓋 | 跨程序的批次租約 |
| 按「完成」略過待確認 | 待確認項目永遠找不回來 | 首頁顯示「上次匯入還有 N 項待確認」 |

## 測試方法的限制

- **代理不等於正式 API**：
  - 子代理沒有結構化輸出的強制格式。
  - 子代理沒有拿到手機端 OCR 文字（正式流程會有）。
  - 第二意見與擷取是同等級模型。
  - 子代理讀圖時常自行裁切放大小字，正式 API 只看到一張縮放後的圖。
- **tesseract 不等於 Apple Vision**：tesseract 對中文與小字明顯較差。OCR 可靠度加權讓系統對 OCR 品質不敏感，但實機 Vision 的影響仍需驗證。
- **模擬名片不等於真實名片**：沒有彎曲、手指、實際鏡頭光學與手寫字。保留集與開發集使用同一個產生器的詞庫（公司名與人名會有重複），它是新的組合，但不是新的分布。
- **樣本小**：75 人、105 張。一個人約等於 2–3 個百分點。
